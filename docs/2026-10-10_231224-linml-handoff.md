# LinML Integration Layer Implementation Plan

> **For Hermes:** Use the subagent-driven-development skill if available to implement this plan task-by-task. Otherwise use TDD and separate implementation and review passes. This document is a handoff, not authorization to modify Trackdub or publish anything.

**Goal:** Build a small Linux-first inference integration prototype that provides honest provider discovery, explicit selection, ONNX inference, and diagnosable fallback without forking Windows ML.

**Architecture:** Use ONNX Runtime as the execution engine. Separate application-facing contracts, selection policy, runtime/provider adapters, and CLI diagnostics. First ship app-local, in-process deployment; system-wide deployment and media-buffer interop are later experiments.

**Tech Stack:** .NET 10, C#, ONNX Runtime C# binding, xUnit, Linux x64. Pinned versions: .NET SDK 10.0.401, `Microsoft.ML.OnnxRuntime` 1.31.0, `Microsoft.ML.OnnxRuntime.Gpu` 1.31.0 (CUDA 13.0 build). This is a managed prototype, not a promised stable cross-language ABI.

## Environment & Build Workflow

**Host:** Windows 11 with WSL2 (Ubuntu 26.04.1 LTS, glibc 2.43, kernel 6.18.40).

**GPU:** NVIDIA GeForce RTX 5070 (Blackwell, sm_120, 12GB VRAM), driver 617.42 / CUDA 13.4. CUDA toolkits in WSL: 12.9, 13.3 at `/usr/local/cuda*`.

**Build & Test Strategy:** All builds and tests run **inside WSL2** (Linux-native). The Windows host provides the filesystem and GPU passthrough; the .NET SDK is installed in WSL via the official install script. This matches the Linux x64 target and provides direct CUDA access.

**WSL2 Setup (Gate A prerequisite):**
```bash
# In WSL2 Ubuntu:
wget https://dot.net/v1/dotnet-install.sh -O /tmp/dotnet-install.sh
chmod +x /tmp/dotnet-install.sh
/tmp/dotnet-install.sh --channel 10.0 --install-dir ~/.dotnet
# Add to PATH: export PATH="$HOME/.dotnet:$PATH"
# Verify: dotnet --version  # Should show 10.0.x

# Verify GPU visibility:
nvidia-smi  # Should show RTX 5070
ls /usr/local/cuda/lib64/libcudart.so*  # CUDA runtime present

# Verify ORT native deps (after publish):
ldd artifacts/publish/linux-x64/libonnxruntime.so  # No "not found"
```

**ORT Package Selection (investigated 2026-10-10):**

| Package | Version | CUDA Build | Rationale |
|---------|---------|-----------|-----------|
| `Microsoft.ML.OnnxRuntime` | 1.31.0 | N/A (CPU) | Latest stable, CPU baseline |
| `Microsoft.ML.OnnxRuntime.Gpu` | 1.31.0 | CUDA 13.0 + cuDNN 9.x | Default since ORT 1.27; compatible with driver 13.4 via minor version compatibility |

**Fallback:** If the CUDA 13.0 build fails on RTX 5070, use `Microsoft.ML.OnnxRuntime.Gpu` 1.31.0 CUDA 12.x variant (requires CUDA 12.8+, we have 12.9 and 13.3 toolkits).

**GPU Distribution Strategy:** Use `Microsoft.ML.OnnxRuntime.Gpu` which includes CPU EP fallback. The GPU package can execute CPU-only workloads on hosts without NVIDIA libraries — verify this in Gate A step 3. If the GPU package cannot run CPU on a CUDA-less host, ship two native flavors (CPU-only and GPU) selected at publish time by RID + flavor.

### Gate A: Select the native runtime and packaging strategy

- ORT managed: `Microsoft.ML.OnnxRuntime` 1.31.0
- ORT GPU: `Microsoft.ML.OnnxRuntime.Gpu` 1.31.0 (CUDA 13.0 build)
- Target RID: `linux-x64`
- Deployment: Framework-dependent, app-local native libraries

Steps:
1. Run `scripts/setup-wsl.sh` in WSL2 to install .NET 10 SDK and verify GPU visibility.
2. Create `global.json` pinning SDK 10.0.401 with `rollForward: latestPatch`.
3. Create `Directory.Packages.props` with pinned ORT packages (see table above).
4. Verify GPU package can execute CPU-only on a CUDA-less host: create a minimal test that loads `Microsoft.ML.OnnxRuntime.Gpu` and runs CPU inference without CUDA libraries. If this fails, plan two native flavors.
5. Run `dotnet restore --locked-mode` and commit `packages.lock.json` files.
6. Write ADR 0001 documenting: SDK version, ORT versions, CUDA compatibility matrix, deployment strategy, licensing (ORT is MIT, .NET is MIT).

Done when: `dotnet restore --locked-mode` succeeds in WSL, the ADR documents actual inspected packages, and a minimal CPU inference runs from the restored packages. Unknown compatibility is marked unknown, not promised.

### Gate B: Define contracts and test selection

Files: `src/LinML.Contracts/*`, `src/LinML.Policy/*`, `tests/LinML.Policy.Tests/*`.

**Logging:** Use `Microsoft.Extensions.Logging` with `ILogger<T>`. Logs go to stderr in the CLI; tests use `NullLogger` or in-memory sinks. No `Console.WriteLine` for diagnostics.

Contract requirements:
- Discovery: provider identity, optional device identities, hardware evidence, ORT provider listing, diagnostics.
- Readiness: load/append/smoke phases and explicit failure reasons.
- Selection: ordered candidate IDs, soft versus required selection, model identity and options.
- Execution: requested/selected provider, fallback chain, tensors, diagnostics, durations.
- Session lifecycle: explicit disposal; cancellation semantics documented honestly.

Test-first cases (14 total):
1. CPU-only host selects CPU.
2. Hardware detected but provider absent does not select CUDA.
3. Listed CUDA provider with failed readiness is rejected.
4. Soft CUDA selection falls back with its original failure reason.
5. Required CUDA selection fails without a successful CPU result.
6. Cancellation propagates and does not trigger fallback.
7. Invalid input/model is not retried as a provider-unavailable error.
8. Selection is deterministic under the same observations.
9. Multiple providers available, selection respects priority order.
10. Discovery report contains all required fields (identity, device, ORT version, diagnostics).
11. Readiness probe distinguishes failure phases (load → append → smoke).
12. Model identity is preserved through selection → execution.
13. Empty candidate list returns typed error, not exception.
14. Concurrent selection calls are thread-safe.

Done when: the hardware-independent suite proves these 14 cases with scripted probes (mock `IProviderDiscovery`, `IProviderReadinessProbe`), without wall-clock timing assumptions.

### Gate D: Add CUDA with honest fallback

**Status: EXPECTED TO PASS** — RTX 5070 (Blackwell, sm_120) with CUDA 13.4 driver is available in WSL2. CUDA toolkits 12.9 and 13.3 installed at `/usr/local/cuda*`.

Files: `Providers/CudaProviderAdapter.cs`, `Providers/CudaReadinessProbe.cs`, `tests/LinML.Runtime.Onnx.Tests/*`, `tests/LinML.Integration.Tests/*`.

**Hardware:**
- GPU: NVIDIA GeForce RTX 5070 (12GB VRAM, Blackwell architecture, compute capability 12.0)
- Driver: 617.42 (CUDA 13.4)
- WSL CUDA toolkits: 12.9, 13.3
- ORT target: `Microsoft.ML.OnnxRuntime.Gpu` 1.31.0 (CUDA 13.0 build — compatible via minor version compatibility)

Steps:
1. Discover CUDA provider support from the loaded ORT runtime (`OrtEnv.GetAvailableProviders()`), not `nvidia-smi` alone.
2. Check actual native loading: `SessionOptions.AppendExecutionProvider_CUDA()` succeeds.
3. Session append: create `InferenceSession` with CUDA EP, verify no fallback warning.
4. Run the Gate C fixture (MatMul+Add) on CUDA — verify output matches expected within `rtol=1e-5, atol=1e-6`.
5. Use ORT profiling (`SessionOptions.EnableProfiling`) to confirm nodes executed on CUDA EP, not CPU partition. Session preference alone is not GPU execution proof.
6. Compare CPU vs CUDA output; test both hard (`--require-provider`) and soft requests.
7. Simulate missing dependency/append/smoke errors with fakes; also test real failure path by temporarily hiding CUDA libraries (`LD_LIBRARY_PATH` manipulation).
8. Avoid a persistent readiness cache in MVP. If later added, key it by model checksum, runtime/provider version, device, and relevant options.

Done when: real Linux CUDA execution is proven in WSL2 with profiling evidence showing CUDA EP assignment. If RTX 5070 compatibility fails with ORT 1.31.0 CUDA 13.0 build, try the CUDA 12.x variant of 1.31.0. If both fail, mark gate blocked with specific error evidence.

### Gate E: CLI and native publishing

Files: `src/LinML.Cli/*`, `scripts/verify-linux-publish.sh`, `docs/diagnostics-schema.md`, `docs/input-schema.md`, `README.md`.

**Public command contract:**

```bash
linml --version                          # CLI version + ORT version
linml providers list --json              # Discovery report
linml doctor --json                      # Readiness report (no downloads)
linml run --model model.onnx --inputs inputs.json --provider cpu --json
linml run --model model.onnx --inputs inputs.json --provider cuda --json
linml run --model model.onnx --inputs inputs.json --provider cuda --require-provider --json
```

**Exit codes:**

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Execution failure (inference error, model load failure, tensor mismatch) |
| 2 | Invalid arguments (bad flags, missing files, parse errors) |
| 3 | Required provider unavailable (hard selection failed, no fallback) |
| 4 | Unexpected/internal error (bug, not user error) |

**CLI behavior:**
- `--provider` is soft selection by default; `--require-provider` disallows whole-session fallback.
- Document separately whether CPU graph partitioning is permitted inside a CUDA session; strict all-GPU execution is not implied.
- JSON diagnostics on stdout remain machine-readable; logs go to stderr.
- `doctor` performs no downloads and does not claim model readiness unless explicitly given `--model` and executing a probe.
- `--version` prints CLI version and ORT managed/native versions.
- Native payload selection follows target RID (`linux-x64`), not the build host.
- Verify the published directory, not only a build tree.

**`verify-linux-publish.sh` checks:**
1. Executable exists: `test -x linml`
2. `ldd linml` and `ldd libonnxruntime.so` show no "not found"
3. `./linml --version` exits 0 and prints version info
4. `./linml providers list --json` exits 0 and prints valid JSON
5. `./linml run --model <fixture> --inputs <fixture-inputs> --provider cpu --json` exits 0

Done when: command tests cover parse/error behavior for all exit codes, actual CPU commands work from published output in WSL2, and `ldd` inspection reveals no unexplained missing dependencies. Framework-dependent deployment requirements are explicit in README.

## Deferred work

Not part of MVP:
- AMD MIGraphX, Intel OpenVINO, QNN/NPU and TensorRT-RTX adapters.
- Automatic performance benchmarking and power-policy selection.
- Persistent device/model compatibility caches.
- C ABI or language SDKs beyond C#.
- System daemon, multi-user sharing, distro packages, Flatpak runtime extensions.
- DMA-BUF, VA-API, PipeWire, Vulkan external-memory interoperability.
- Zero-copy claims, shared model caches, worker isolation for untrusted models.
- Trackdub integration.

Each provider addition requires its own dependency/redistribution decision, session adapter, negative-path tests, model smoke evidence, and supported-hardware matrix. Media interop requires buffer format, ownership, synchronization, and provider compatibility experiments before an API promise.

## Risks and decisions needing evidence

- A common API does not make native dependency requirements common across vendors.
- Real-provider append/smoke can fail at the native level; in-process MVP does not provide crash isolation.
- Model-specific optimized artifacts may not be portable across providers.
- CPU partitioning can make a nominal GPU session misleading without profiling.
- Synchronous ORT execution needs a deliberate termination/cancellation design; Task.Run alone is not cancellation.
- **WSL2 GPU passthrough** provides CUDA access, but WSL2 is not bare-metal Linux. Performance and some driver behaviors may differ from native Linux. Document this in compatibility.md.
- **RTX 5070 (Blackwell, sm_120)** is a recent architecture. If ORT 1.31.0 CUDA 13.0 build lacks kernels for sm_120, Gate D may need the CUDA 12.x variant or a newer ORT build.
- .NET SDK must be installed in WSL2 separately from the Windows installation. The `setup-wsl.sh` script automates this.
